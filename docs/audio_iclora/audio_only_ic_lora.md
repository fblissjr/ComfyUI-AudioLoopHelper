# Audio-only IC-LoRA: how it works, how to run it, how to eval it

An audio-only IC-LoRA for LTX-2.3-22B (distilled): an in-context reference **audio** clip (here, a voiced
tone) steers an attribute of the jointly-generated audio+video. There is no image or video reference. The
test attribute is pitch ("helium"), chosen because it is measurable, the base model does not already do it,
and only the audio reference can carry it. This is a proof of concept; whether it cleanly steers pitch at
inference is still under evaluation. Full write-up, data recipe, and checkpoints are on the model card (the
LTX-2 fork, `audio_reference` strategy).

## How the custom nodes work

All three live in `nodes_audio_iclora.py` and are debug-instrumented (they log to the ComfyUI console).

- **`LTXAudioICLoRALoader`**: loads the audio IC-LoRA onto the model and logs key-match telemetry. It
  **fails loud**: if the LoRA binds zero patches to the model it raises, instead of returning a no-op model.
  A wrong base model or a mangled checkpoint can otherwise look exactly like a null eval result, so this gate
  stops the run with a diagnostic rather than letting a dead adapter produce a meaningless measurement.
- **`LTXVAudioVAEEncode`** (stock ComfyUI-LTXVideo) then **`LTXAudioSetRefTokens`**: encode the reference
  tone to a latent, then patchify it into `ref_audio` tokens and attach them to the positive and negative
  conditioning. The patchify (`(b, c, t, f) -> (b, t, c*f)`) is byte-identical to stock
  `LTXVSetAudioRefTokens`; matching that layout is the train/inference parity, because the model offsets
  whatever reference tokens it finds.
- **`LTXAddAudioICLoRAGuide`**: an all-in-one alternative to the two nodes above: raw audio in, it encodes,
  patchifies, and attaches in a single node.

The model (LTX-2) places the reference tokens at **negative RoPE positions**, i.e. as out-of-timeline
context rather than part of the generated timeline (the ID-LoRA convention). That is what lets a reference
steer an attribute without being something the model has to reproduce frame-for-frame. This mechanism suits
**time-invariant** attributes (an average pitch, a timbre, a voice); it is not built for time-varying control.

## How to run it in ComfyUI

1. Put the LoRA in `models/loras`.
2. Model chain: your UNET loader, then `LTXAudioICLoRALoader` (the IC-LoRA loader, not the generic one),
   into your guider.
3. Reference: `LoadAudio` (a voiced tone) into `LTXVAudioVAEEncode` into `LTXAudioSetRefTokens`, attaching to
   the positive and negative conditioning. Keep the caption constant and pitch-free.
4. Generate audio and video together (do not freeze the audio latent). Save with `VHS_VideoCombine` so the
   video and audio are muxed into one file.
5. Precision: the reference is encoded by the audio VAE in **fp32**, matching how the training data was
   encoded. You do not have to set anything for this. comfy always runs the LTX audio VAE in float32 (it
   forces it, and VAELoaderKJ's audio path ignores the dtype widget), so the parity holds automatically. The
   LoRA itself is bf16.

## How to evaluate it (the F0-tracking gate)

The eval is the verdict: does the reference tone's pitch steer the generated speech's pitch, beyond what the
base model does on its own.

- **Two arms, identical except the LoRA**: base (the loader bypassed) versus base+LoRA. Same seed, same
  constant caption, same reference tone, same dimensions (256x256, 121 frames, 25 fps).
- **Sweep** the reference tone's F0 across the in-range band. For each arm, measure the generated speech's F0
  (for example with pyin or torchcrepe) and regress output-F0 on reference-F0. A LoRA slope near 1 (the
  output tracks the tone) versus a base slope near 0 (flat) means the reference is load-bearing.
- The eval workflow template is generated by `scripts/build_pitch_gate_eval_workflow.py`. It forks the proven
  stock single-stage A+V distilled graph, keeps only the distilled sampler chain, and splices in the audio
  reference, a constant caption, a LoRA-arm toggle, and a `VHS_VideoCombine` save.

## The automated trust gates

An eval you cannot trust is worse than no eval: a subtly broken apparatus turns a null into noise and a
positive into a mirage. These checks fail loud rather than silently:

- **Dead-LoRA gate (runtime):** `LTXAudioICLoRALoader` raises if the LoRA binds zero patches. A wrong base
  model or mangled checkpoint cannot produce a fake null.
- **Grammar gate (offline, unit-tested):** `lora_grammar_problems()` checks the checkpoint is the
  `diffusion_model.<...>.lora_A/lora_B.weight` grammar comfy can map, the necessary condition for the loader
  to bind it.
- **Reference-encode parity:** the audio VAE runs in fp32 (comfy forces float32 for the LTX audio VAE),
  matching the training encode, so the reference latent does not drift off what the LoRA trained on.
- **Patchify parity:** the reference-token layout is byte-identical to the stock node (the train/inference
  parity), confirmed against the stock source.
- Tests: `tests/test_audio_iclora_guide.py` (the patchify contract and parity, the reference-token attach,
  the encode invocation, the dual-mono widening, and the grammar gate).

## Honest caveats

- Inference efficacy is unproven until the F0 slope (LoRA versus base) is published.
- The training data has a known confound: the target pitch correlates about 0.75 with the clip's own natural
  pitch, so a null result is ambiguous (the model could lean on the speaker's identity rather than the
  reference). The model card covers this and the next-run designs (reuse each clip at several pitches to
  break the confound; voice transfer as the natural follow-up).
- The base model was trained jointly on audio and video. Isolating an audio-only reference is a deliberate
  test, and it is possible the attribute is only steerable with video coupled in.
